# Security and operational boundaries

## Implemented baseline

- Jira credentials are loaded locally, with `SecretStr` masking. `.env` is ignored.
- Live Jira requires an HTTPS `*.atlassian.net` site origin. Demo HTTP is restricted
  to loopback. Redirects are not followed, preventing auth forwarding to another site.
- Explicit HTTP timeouts; bounded retries on transient GET responses only. Writes
  are never automatically retried. Long `Retry-After` instructions are surfaced.
- Safe errors omit upstream response bodies, tokens, request headers, and raw exceptions.
- Validated project/issue keys, issue types, summary lengths, and nonempty updates.
- REST business endpoints require a HALO API key. The CLI binds REST to loopback.
  Swagger documents the API key. The unauthenticated health check returns no credentials.
- CLI live writes require `--allow-live-write`. REST/MCP writes rely on access to the
  already-authorized local server. Treat all MCP hosts and callers as trusted operators.
- REST correlation IDs are generated by the service. Structured audit logs contain
  route templates, method, status, duration, and correlation ID, excluding payloads.
- The MCP workflow subprocess receives Jira and required network settings, excluding
  unrelated cloud/GitHub secrets. It writes protocol output only to stdout.
- Tests use explicit fake settings. The end-to-end demo targets loopback with public
  simulator credentials and cannot silently use live `.env` values.
- SQLite workflow state is excluded from Git and restricted to owner access on POSIX.
- Docker excludes `.env`, Git history, local state, and virtual environments; runs non-root.

## Workflow duplicate prevention and recovery

The local SQLite store claims a unique execution ID before any network write. It
binds that ID to the full workflow specification, route, and Jira site/account.
A matching paused or completed run is returned without creating another issue.
A changed specification is rejected. Approval atomically claims a paused execution.

State is saved immediately after receiving a created task or bug key. A failure
moves the execution to `needs_review`. A crash can leave `running`. Either state
blocks automatic replay, because a remote write could have succeeded before its
response was lost. Retain the database; deleting it removes duplicate protection.

For recovery, inspect the execution record and the dedicated Jira project. Search
for the execution ID in the issue description. Record any existing Jira key before
considering another write. There is no automatic reset or recovery command. Have
a developer reconcile state against Jira rather than deleting rows and rerunning.
This is conservative local duplicate prevention, not an exactly-once distributed
transaction. Direct REST and MCP create calls have no generic idempotency guarantee.

## Enterprise work still required

The static local HALO API key is not enterprise identity or per-user authorization.
Before shared deployment, add corporate OIDC/OAuth, scoped authorization, credential
vaulting and rotation, TLS, ingress controls/rate limits, tamper-resistant audit
storage, and centralized policy enforcement. Do not distribute Jira credentials
with desktop applications; host the Jira capability centrally in that design.

The custom MCP server exposes local stdio only. A hosted Streamable HTTP deployment
must validate tokens, audience, scopes, origin, and session policy under the current
MCP specification; a REST API key is not an MCP OAuth implementation.

Jira writes are not destructive or bulk operations in the demo. No real Jira write
was performed during this build. Attachments, assignment, links, custom-field
mapping, transitions requiring extra fields, and distributed workflow recovery
remain outside this prototype. No service has been exposed publicly.
